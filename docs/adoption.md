# チートシートのうち「今この repo で使うもの」

チートシートは100項目あるが、この repo は現状 `readme.md` 一行（「会社を作るため」）だけ。
成熟度レベルで言えば **1（学習）から 2（構築）に入るところ**。
100項目を一度に導入するのは「小さく始めて段階的に拡張」というベストプラクティス自体に反するので、
**いま採る / 次に採る / まだ採らない** を明示的に分ける。

## いま採る（この repo に実体がある）

| チートシート項目 | この repo での実体 |
|---|---|
| 21 役割 / 22 目標 / 23 コンテキスト | `CLAUDE.md`（Claude が毎回読む常設コンテキスト） |
| 41 目的定義 / 42 成功条件 / 44 出力形式 | `prompts/task-template.md` の必須欄 |
| 45 ステップ分解 / 50 プロンプト改善 | 同テンプレの「手順」「反例」欄 |

| 開発チェックリスト | `docs/checklist.md` を PR 前に通す |
| 成熟度レベル | この文書自体。レベルを上げたら追記する |

  使わない連携を最初から繋ぐとコンテキストを食うだけ）。
- 70 自動化連携 (CI) — テストが1つでもできてから。

## まだ採らない（今やると過剰）

- 71–80 監視ぜんぶ（動いているエージェントが無い）
- 84 キャッシュ / 85 並列化（最適化する負荷が無い）

「まだ採らない」に入れた理由は、後で状況が変われば覆るというだけの話なので、
覆すときはこの表を書き換えること。

## 運用ルール（チートシートから抽出した実行可能な分だけ）

1. **目標と成功条件を書いてから頼む。** 42「成功条件」が無い依頼は、出来上がりの良し悪しを誰も判定できない。
2. **出力形式を指定する。** 44。「まとめて」ではなく「Markdown の表で、列は A/B/C」。
3. **人間確認を挟む。** 30/49。外部送信・課金・削除・公開は必ず人間が最終判断する。
4. **ドキュメントが真実源。** 68。決定事項をチャットログに置いたままにしない。`docs/` に落とす。
5. **検証を頼む。** 55/65。「やった」ではなく「どう確かめたか」を出力に含めさせる。
6. **小さく作る。** 51。1回のタスクは1つの成果物まで。
